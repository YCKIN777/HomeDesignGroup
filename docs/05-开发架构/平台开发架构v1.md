# 家装 AI 智能体平台 · 开发架构 v1（搭建蓝图）

> 状态：定稿 v1｜更新：2026-09-29｜存放：HomeDesignGroup/docs/05-开发架构/
> 用途：**你照着"资料准备清单"准备资料；平台按五个阶段有序推进。** 结构锁定（内核 v0.2），迭代只发生在扩展点。

---

## 1. 总架构（锁定，不再讨论）

```
平台 = 内核 + 配置 + 数据 + 回路
├── 内核 v0.2（锁定）：八阶段主链 · 状态机主干 · 核心概念 · Agent框架 · 数据主线 · 沉淀原则
├── 配置包（壹城精工第一家）：术语/规则值/扩展字段/节点配置/知识库
├── 数据：客户CRM · 项目（起步两张表）
└── 回路：试跑 → 提炼 → 沉淀中心 → 反哺扩展点（封闭项不动）
```
详细锁定项/扩展点见 `通用内核v0.2-最小可信版.md`。

## 2. 技术分层（开发视角）

| 层 | 内容 | 说明 |
| --- | --- | --- |
| 接入层 | 渠道接入（企微/微信/抖音/小红书/电话）、浏览器扩展 | 第一阶段先做"人工录入+Excel导入"兜底，渠道自动接入后置 |
| 应用层 | 前端智能体工作台（销售/客服/主管 Web UI）· 统一收件箱 · 派单面板 · 看板 | 参照 LinkedNav 产品形态（Dashboard/Unibox/Prompts） |
| 服务层 | Agent 运行时（中控+子Agent）· 规则引擎 · 知识库检索 · 消息通知 | 复用现有原型模式：消息总线、/pause /reject 指令、配置加载 |
| 数据层 | 客户CRM表 · 项目表 · 配置库（术语/规则/扩展）· 沉淀池 | 起步两张主表；配置全读文件，不写死 |

## 3. 模块清单与优先级（前端智能体 MVP）

## 4. 开发阶段（有序推进）

| 阶段 | 内容 | 产出 | 完成标志 |
| --- | --- | --- | --- |
| 阶段0 资料与定稿 | 你准备资料；定稿配置包模板+沉淀模板 | 壹城精工配置包雏形 | 资料清单 A/B/C 到位 |
| 阶段1 骨架 | 数据库+配置加载器+Agent运行时骨架+工作台框架 | 可运行空框架 | 空框架能启、能读配置 |
| 阶段2 MVP闭环 | M1-M5 | 获客→派单闭环 | 全链路人工走通 ★ |
| 阶段3 能力增强 | M6-M9 | 前端智能体功能齐 | 各功能演示通过 |
| 阶段4 试跑沉淀 | 壹城真实试跑1个月；提炼→沉淀中心；扩展点迭代 | 首批沉淀物+迭代记录 | 沉淀池≥5条优质物，配置包迭代≥2轮 |

**阶段依赖**：0→1→2 串行；3 依赖 2；4 依赖 3（试跑需要功能齐）。

## 5. 资料准备清单（你按阶段准备）

### A. 业务规则类（填配置包 · 阶段0）
1. 报价结构（构成项/套餐档位）
2. 付款比例与节点
3. 折扣审批阈值与权限
4. 跟进 SOP 节奏（首联时限/跟进频率）
5. 施工验收节点划分
6. 质保年限与范围
7. 组织分工（销售/设计师/项目经理/监理人数）
8. 主要获客渠道与占比

### B. 样本数据类（喂系统 · 阶段1-2）
9. 历史报价单 3-5 份（用于报价口径校准，D1 项）
10. 真实跟进/客服对话记录样例（脱敏，用于话术与收件箱测试）
11. 客户台账样例（字段参考）
12. 楼盘/户型信息（长沙主要楼盘，B1 项）

### C. 知识内容类（挂知识库 · 阶段3）
13. 公司完工案例 3-5 个（图文）
14. 工艺卖点/施工标准资料（E 类已有公开资料，补公司版）
15. 现行合同模板（F2 项）
16. 套餐宣传资料/谈单话术素材

## 6. 里程碑与验收

| 里程碑 | 验收标准 |
| --- | --- |
| M1 骨架可用 | 空框架启动、读配置、两张表建好 |
| M2 MVP 闭环 | 线索录入→建档→AI起草→销售审批→发送→派单建项目 全链路人工走通 |
| M3 功能齐 | M6-M9 演示通过，谈单知识库可检索 |
| M4 试跑完成 | 壹城试跑 1 个月；沉淀池≥5 条优质提炼物；配置包迭代≥2 轮；封闭项零改动 |

## 7. 风险提示（来自 v2 优劣势分析）

1. 前期只做单公司能跑通的子集，多租户后置
2. 配置槽位收敛，配"配置向导"，防配置地狱
3. 沉淀先人工，跑通再半自动
4. 一切语义走配置，代码不写死（M5 是关键）
5. 封闭项变更走版本升级+评审，日常只动扩展点

## 9. 开发架构 v1 优劣势分析（2026-09-29）

### 9.1 优势（9）

| # | 优势 | 说明 |
| --- | --- | --- |
| 1 | 范围收敛可执行 | MVP 只有 5 个模块（M1-M5），不是空谈 |
| 2 | 阶段依赖清晰 | 0→1→2→3→4 每阶段有产出+验收，有序推进（正是你要的） |
| 3 | 资料与阶段对齐 | 资料清单 A/B/C 映射到阶段，你明确知道"备什么、什么时候用" |
| 4 | 贯彻内核锁定 | M5 配置加载是关键设计：一切语义走配置，不写死，结构锁定有落点 |
| 5 | 里程碑可验收 | 验收标准是"走通/演示/计数"，不是"差不多" |
| 6 | 复用原型资产 | 消息总线、/pause /reject、配置加载模式直接复用，少从零造 |
| 7 | 人审后发内置 | M3 统一收件箱把"You approve"原则落成第一个核心模块 |
| 8 | P2 后置明确 | 社交监听/账号池/多租户明确后置，不背大工程 |
| 9 | 技术分层简单 | 四层够用，不过度工程（不上微服务） |

### 9.2 劣势与风险（9）

| 级别 | # | 劣势/风险 | 说明 | 应对 |
| --- | --- | --- | --- | --- |
| 🔴 高 | R1 | **M3 收件箱是隐藏重活** | AI起草+审批+渠道直连（企微/微信），工作量≈其他 4 个模块之和；渠道接不通则 MVP 卡死 | **M3 拆两步**：M3a AI起草+审批+复制/发送模板（本阶段）；M3b 渠道直连（后置） |
| 🔴 高 | R2 | **阶段 0 卡资料** | A 类 8 项给不齐，阶段 0 卡死；文档串行 = 骨架开发干等 | 阶段 0/1 并行：骨架不等资料，配置加载器按通用格式先做，资料后填 |
| 🟠 中 | R3 | MVP 范围未经验证 | 无真实线索量/渠道占比，M1 归集形态可能返工（如实际靠抖音私信，Excel 导入就不是重点） | 阶段 2 用 3-5 条真实线索全链路跑一遍校准 |
| 🟠 中 | R4 | 验收偏演示级 | 阶段 2/3 是"走通/演示"，无业务指标 | 阶段 4 补：24h 首联率/响应时长中位数/派单及时率 |
| 🟠 中 | R5 | 技术选型未定 | 工作台 React 还是简单页未定，定了才不返工 | 这是下一确认项，先按"简单 Web 页起步"假设推进 |
| 🟡 低 | R6 | 知识库(M9)范围粗 | 挂什么、检索质量怎么验收未定，易变文档堆 | 阶段 3 前定知识库清单+检索验收样例 |
| 🟡 低 | R7 | 模块边界细碎 | M2/M7 跟进记录边界，实现时易扯皮 | 实现前过一遍字段归属表 |
| 🟡 低 | R8 | 流程假设未校准 | 派单若是"群发"而非"单派"，改扩展点还是封闭项需现场判断 | 立纪律：假设错→先判扩展点/封闭项，禁随手改内核 |
| 🟡 低 | R9 | 单点人力依赖 | 全程一人开发，试跑期 bug 修复与迭代抢时间 | 试跑期降速保稳，迭代走沉淀流程 |

### 9.3 关键判断

- **优势在"可执行、有序、贯彻锁定"**；劣势集中在三处：**M3 渠道接入是隐藏重活、阶段 0 用户是瓶颈、范围靠假设待真实业务校准**。
- 这套架构不需要再改——按 9.2 的 5 条对冲动作调整推进方式即可：**M3 拆两步、阶段0/1并行、真实验证进验收、业务指标补阶段4、流程假设立纪律**。
