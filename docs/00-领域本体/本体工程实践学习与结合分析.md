# 本体工程实践学习与结合分析

> 状态：学习笔记 + 结合方案｜更新：2026-09-29｜存放：HomeDesignGroup/docs/00-领域本体/
> 目的：从 GitHub/W3C 本体工程实践学习"正规做法"，评估与家装平台轻量本体的结合点。
> 结论一句话：**你的轻量本体方向正确，但缺四样东西——文本定义、ID 稳定性纪律、关系白名单、配置校验器。补齐后它就是"轻量但正规"的领域本体。**

---

## 1. 我学到的（来源可追溯）

### 1.1 OBO Foundry 原则（生物医学本体社区的标准，公认的好实践）
来源：https://obofoundry.org/principles/fp-000-summary.html

与家装平台直接相关的 8 条：

| 原则 | 内容 | 为什么重要 |
| --- | --- | --- |
| P2 通用格式 | 本体必须用公认形式语言发布 | 我们：md/yaml 统一格式即满足（不必 OWL） |
| P3 URI/ID 空间 | 每个本体有唯一 ID | 我们：概念 ID 唯一且稳定 |
| P4 版本化 | 版本标记、存储、正式发布 | 我们：内核 v0.2→v0.3 流程 |
| P5 范围 | 明确覆盖领域，不越界 | 我们：前端智能体范围锁定（获客→派单） |
| P6 文本定义 | 多数类必须有文本定义（"一个X，其特征Y"） | **我们最缺：术语只有名字没有定义** |
| P7 关系复用 | 复用已有关系，不发明 | **我们最缺：关系随意造** |
| P12 命名唯一 | 标签唯一 | 我们：术语表唯一性 |
| P19 术语稳定 | 定义所指永不变；变语义=新ID新定义 | **我们最缺：改语义的纪律（与沉淀中心直接相关）** |

### 1.2 W3C OWL 2（本体形式化语言标准）
来源：https://www.w3.org/TR/owl-primer/ · https://www.w3.org/TR/owl-quick-reference/

核心心智模型（不用文件格式，但按这个建模）：
- **类层级**：单一继承（线索⊂客户？不——线索"升级为"客户是状态迁移，用状态机表达，不用子类）
- **公理**：子类、等价、互斥（DisjointClasses）
- **属性**：对象属性（关系）/ 数据属性（字段）；domain/range 域与值域
- **约束**：基数（一个客户至少 1 条跟进）、取值限制

### 1.3 DOS-DP：Dead Simple OWL Design Patterns（GitHub INCATools）
来源：https://github.com/dosumis/dead_simple_owl_design_patterns
被 ENVO / Uberon / Mondo 等生物本体采用。

**最契合你的做法**，因为它本身就是 YAML 写本体模式：
- YAML 写模式（可读、可加注释、可转 JSON）
- **变量插值**（printf 格式：`{客户姓名}`、`{楼盘}`）
- **Python 校验器**（src/simple_pattern_tester.py）：填错当场报错，不憋到运行
- 模式生成文档、生成新术语、批量改造旧术语

→ 直接映射：你的 terms.yaml/rules.yaml/workflow.yaml 就是"DOS-DP 模式"；补一个 schema 校验器即可。

### 1.4 其他学到但现阶段只记录
- **ODP 模式库**（ontologydesignpatterns.org）：可复用建模模式；八阶段状态机 = 生命周期模式
- **gUFO**（arXiv 2603.20948）：温和上本体，用于知识图谱；现阶段过重
- **OLIVAW 模板**（GitHub Wimmics/Olivaw-Template）：协作本体开发目录结构（src/模块 + domains/场景）——与我们工程目录天然一致
- **FAIR 本体实践**（arXiv 2003.13084）：属性域/值域明确、等价/逆属性表示

## 2. 与你的家装平台结合方案（保持轻量）

### 2.1 直接采用（马上做）

| # | 实践 | 落到哪里 | 动作 |
| --- | --- | --- | --- |
| 1 | P6 文本定义 | **terms.yaml 升级术语注册表** | 每词条 {id, label, 定义, 父类, 来源, 状态}；定义句式"一个X，其特征Y" |
| 2 | P19 术语稳定 | **内核锁定 + 沉淀中心** | 提炼物进池带 ID/定义/来源；语义变更=新概念新 ID，绝不改旧 ID 含义 |
| 3 | P7 关系复用 | **关系白名单** | 通用关系≤5（part_of / preceded_by / has_participant / has_responsible / derived_from）+ 领域关系明确域/值域 |
| 4 | OWL 公理心智 | **workflow/rules.yaml 公理化** | 状态迁移带触发条件+强约束；互斥状态（如"签约"与"流失"互斥） |
| 5 | 能力问题 CQ | **Agent 能力清单** | 每个子 Agent = 一组业务问题；校验本体覆盖 Agent 所需概念 |
| 6 | DOS-DP 校验器 | **config_loader.py 加 schema 校验** | 配置填错当场报错；话术模板支持 {变量} 插值 |
| 7 | P4 版本化 | **内核发布流程** | v0.2→v0.3 带 CHANGELOG + 版本目录 + 评审（你已有，补发布记录） |

### 2.2 借鉴但轻量版
- **生命周期模式**：八阶段状态机 = 标准生命周期本体做法（主干锁定+节点可配，你已做对）
- **类层级/互斥**：概念表加 parent 字段 + 互斥标记（不引入 OWL 推理）

### 2.3 现阶段不引入（记录备用）
- OWL 文件格式 + 推理机（HermiT/ELK）——平台跑通 2-3 家后再评估
- 上本体（BFO/gUFO）——单人平台过重
- SHACL 规范全量——用轻量 schema 校验代替
- Protégé 工具链——你的 md/yaml 工作流不需要

## 3. 落地顺序（不改变当前开发架构）

1. **阶段 1 顺手做**：config_loader.py 带 schema 校验器（对应 DOS-DP 做法）
2. **填壹城配置包时做**：terms.yaml 按术语注册表格式（id/定义/父类/来源/状态）
3. **沉淀中心启用时做**：提炼物格式加"定义+来源+ID 稳定性"字段（对齐 P19）
4. **内核 v0.3 升级时做**：发布记录（CHANGELOG + 版本目录，对齐 P4）
