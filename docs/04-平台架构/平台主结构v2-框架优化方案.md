# 平台主结构 v2 · 框架优化方案（含迭代成长机制）

> 状态：探讨稿 v2｜更新：2026-09-29｜存放：HomeDesignGroup/docs/04-平台架构/
> 目标：主结构**明确、简洁、可控**；同时框架能通过不同公司的数据与经验**不断丰富、迭代升级**。
> 一句话：**平台 = 内核 + 配置 + 数据 + 回路**。

## 1. 主结构（四件事，职责不重叠）

```
┌─────────────────────────────────────────────┐
│ 平台主结构                                   │
│                                             │
│  ① 平台内核（不改 · 版本化）                  │
│     ├── 领域模型（本体：概念/关系/状态机）      │
│     ├── 流程与规则（八阶段 SOP + 规则引擎）     │
│     └── Agent 框架（中控 + 六工种 + 审批）      │
│        ↓ 实例化                                │
│  ② 公司配置包（可换 · 一家一包）                │
│     ├── 术语映射表                            │
│     ├── 规则值（折扣/付款/SOP/质保）            │
│     ├── 扩展概念/字段                          │
│     └── 知识库内容（话术/材料/工艺/案例）        │
│        ↓ 填充                                  │
│  ③ 公司数据实例（可填）                        │
│     ├── 数据库（具体表 + 数据）                │
│     └── 历史数据（报价/合同/工地）              │
│                                             │
│  ④ 迭代回路（成长引擎）                        │
│     公司实践 → 沉淀池 → 分拣 → 评审 → 内核 v+1 │
│                    └→ 个性 → 回配置包          │
└─────────────────────────────────────────────┘
```

**职责划分（可控的关键）**：
| 主件 | 回答的问题 | 谁动它 |
| --- | --- | --- |
| 内核 | 行业逻辑"对不对" | 只有评审通过才升级（受控） |
| 配置包 | 这家公司"怎么叫、怎么定" | 每家公司自己填（开放） |
| 数据 | 这家公司"事实是什么" | 业务系统自动写入 |
| 回路 | 框架"怎么变强" | 平台方治理（分拣+评审） |

## 2. 迭代回路（框架如何被各公司实践喂大）

### 2.1 回路流程
```
公司实践与数据（跑系统时产生）
   ↓
经验沉淀池（候选改进集中地：新概念、新规则、新节点、效果数据）
   ↓
分拣：共性 vs 个性
   ├─ 共性（两家以上公司同样需要 / 行业证据支持）→ 提交评审
   ├─ 个性（仅一家特有）→ 直接进该公司配置包，不惊动内核
   ↓
评审（评审标准：不改坏全链路、不与其他规则冲突、有实例支撑）
   ↓
内核升级 v0.1 → v0.2 → v1.0（版本化 · 向后兼容 · 留 CHANGELOG）
```

### 2.2 分拣规则（示例）
| 场景 | 判定 | 去向 |
| --- | --- | --- |
| 两家公司都用"24h 首联"，且数据证明有效 | 共性 | 内核默认规则（升级） |
| 某公司新增"别墅楼梯专项工艺" | 个性 | 该公司配置包 |
| 行业新规（如 GB 55038 替代旧强条） | 共性（权威证据） | 内核知识库升级 |
| 某公司"周六到店高峰"排班经验 | 个性 | 该公司配置包 |
| 多公司反映"增项扯皮"是普遍痛点 | 共性 | 内核流程/规则升级 |

### 2.3 版本与兼容
- **内核版本**：v0.1（现草案）→ v0.2（定稿通用版）→ v1.0（首个可用发布）……
- **配置包版本**：每个配置包声明"基于内核版本 x.y"；内核升级必须向后兼容（已有配置包照常运行），实在要破坏性变更 → 显式迁移指引
- **变更留痕**：每次内核升级写 CHANGELOG（改了什么、为什么、影响谁）

## 3. 相对 v1 的优化点（响应"简洁可控"）

1. **主结构收敛**：从"三列平铺"简化为"内核 + 配置 + 数据 + 回路"四主件，一眼看懂职责边界
2. **新增迭代回路**：框架从"静态模板"变成"可生长的骨架"——公司的数据/经验不再是死数据，而是框架进化的养料
3. **明确"谁动什么"**：内核受控升级、配置包自由填写、数据自动写入、回路平台治理——四个主件各自的可变权限写死，避免乱改
4. **版本化与兼容**：升级有节奏、有留痕、不破坏已有公司

## 4. 落地到当前资产

| 主件 | 当前状态 | 下一步 |
| --- | --- | --- |
| 内核 | 草案已立（本体 v0.1、流程清单 v1、业务逻辑 v1） | 升级为**内核 v0.2 通用版**（标注封闭项/开放项） |

| 回路 | 机制已定义 | 建立沉淀池目录 + 分拣/评审模板 |

## 6. 优劣势分析（v2 评估）

### 6.1 优势

| # | 优势 | 说明 | 对家装平台意味着什么 |
| --- | --- | --- | --- |
| 1 | 职责边界清晰 | 内核/配置/数据/回路各管一件事，互不干扰，可独立演进 | 单人也能 hold 住，符合"简洁可控"诉求 |
| 2 | 一套内核多公司复用 | 换公司=换配置包+数据，内核零改动 | 边际成本低，这是"平台"与"项目定制"的分水岭 |
| 3 | 定制不写代码 | 术语/规则值/扩展字段/节点全部走配置 | 未来甚至可以让公司老板自己调，不依赖开发 |
| 4 | 框架可成长 | 迭代回路让实践经验反哺内核 | 服务越多公司内核越厚，区别于一次性交付系统 |
| 5 | 风险隔离 | 单公司配置出问题不影响内核和其他公司；内核升级受评审 | 不会因一家公司的特殊需求把全平台带翻车 |
| 6 | 版本化+留痕 | 内核升级有节奏、可回滚、可追溯 | 长期可维护，出问题能定位 |
| 7 | 与 Agent 架构天然契合 | 本体给 Agent 稳定语义，配置包给 Agent 公司上下文，回路给 Agent 校准数据 | 这正是"AI 智能体平台"该有的底座 |
| 8 | 起步门槛低 | 没有数据也能立骨架 | 不阻塞当前推进（正是我们的处境） |
| 9 | 已有资产全部归位 | 本体/流程清单/数据需求清单直接归属主件 | 前面做的活不返工 |

### 6.2 劣势与风险

| # | 劣势/风险 | 说明 | 应对 |
| --- | --- | --- | --- |
| 1 | **通用内核提炼难度大（最大风险）** | "骨架封闭"要求准确区分共性与个性；提炼错→框架僵化或逻辑错。当前没有真实数据支撑，"通用规则"实为行业惯例默认值，存在"假通用" | 内核只锁强约束（八阶段主干/隐蔽工程不可跳过/人审后发/审批点），其余全部默认开放 |
| 2 | 配置地狱风险 | 定制机制设计过细→配置项爆炸，维护成本反超收益；"零代码"变"写配置" | 配置槽位先收敛成 3-4 类，配"配置向导"模板 |
| 3 | 抽象成本高、前期投入大 | 通用框架比单公司定制多一层抽象工作（schema/格式/兼容/文档） | 若最终只服务壹城一家，抽象有一半是浪费——需先确认平台定位 |
| 4 | 回路治理难、易被架空 | 没有分拣评审纪律：沉淀池变垃圾桶/内核频繁升级不稳/个性误判污染内核；收益长期、成本即时 | 回路先人工（沉淀池目录+评审模板），跑通 2-3 家后再半自动 |
| 5 | 向后兼容枷锁渐重 | 公司多了以后，内核每改一处要验证所有配置包，最终可能"动不了"，内核僵化 | 内核升级只做"加法"（加概念/加槽位），破坏性变更显式迁移 |
| 6 | 多公司=多租户工程复杂度 | 数据隔离、权限、报表口径差异、配置冲突——平台级工程量远超单公司系统 | 现阶段只实现单公司能跑通的子集，多租户能力后置 |
| 7 | 配置包谁来填 | 灵活但操作者是业务人；没有配套配置工具/向导，"灵活"只是纸面 | 做"配置向导"（问答式生成配置包），而不是裸表单 |
| 8 | 通用≠好用（平庸化风险） | 通用内核覆盖不到公司核心竞争力（如壹城精工的私人定制工艺细节） | 扩展字段/知识库就是留给核心竞争力的位置，要引导公司用起来 |
| 9 | 回路样本不足（早期） | 只有一家公司时，分拣缺统计依据：一家经验是共性还是个性的判断不可靠 | 前期回路待机，靠行业资料补共性；公司多了再启用 |

### 6.3 关键判断（这套架构什么时候对）

- **假设成立的前提**：你的目标是把平台做成"可复制产品"，服务多家家装公司（通用架构→各公司定制→经验反哺）。从你的表述看，你是这个方向——**架构选择是对的**。
- **如果最终只给自己一家公司用**：v2 的抽象（配置包、回路、版本化）有一半是浪费，单公司定制系统更省。
- **结论**：按平台架构设计，但**分阶段实现**——现阶段先跑通"单公司能用的子集"，平台能力（多租户、回路）后置。

### 6.4 对冲措施（落地建议）

1. 内核 v0.2 采用"最小可信内核"：只锁行业强约束，其余开放
2. 配置槽位收敛为 3-4 类 + 配置向导，防配置地狱
3. 回路先人工、后半自动；前期靠行业资料补共性样本
4. 拿壹城精工做第一家实例化，用真实需求检验内核对不对，再谈扩展
5. 明确"单公司先行、平台后置"的阶段划分，避免一次性背上多租户工程量

## 7. 数据隔离 × 语义共享分离（v2.1 细化）

### 7.1 用户确认的设计
- **数据分离**：每家公司原始数据（客户/报价/工地）物理隔离，永不出公司——客户数据、报价数据是公司核心资产，不存在共享
- **语义分离**：各公司实践提炼出的"优质语义/经验"（规则模式、话术模板、术语模式、最佳实践）进**公共沉淀中心**，去噪去重匿名化后共享
- **沉淀中心**：一个独立的地方单独沉淀优质数据/经验；垃圾数据剔除
- **平台分型**：性质相似的 2-3 类家装公司共用一套平台概念（可整合）；模式/流程差异大的公司不适用
- **结论**：数据分离与语义分离可以分开，而且应该分开——这是行业已验证的做法（原始数据留本地，知识进公共池）

### 7.2 主结构 v2.1

```
① 公司私有区（隔离 · 不共享）
   ├── 公司 A（壹城精工）：私有配置包 + 私有数据
   ├── 公司 B（同类）　　：私有配置包 + 私有数据
   └── 公司 C（同类）　　：私有配置包 + 私有数据
        ↓ 提炼（去噪·去重·匿名化·抽象化）
② 沉淀中心（公共 · 共享）
   只收优质提炼物：规则模式 / 话术模板 / 术语模式 / 最佳实践
        ↓ 分拣 + 评审
③ 平台内核（不改 · 版本化）
   └─ 优质模式可推荐给其他公司配置包（可选，不强制）
```

### 7.3 优势

| # | 优势 | 说明 |
| --- | --- | --- |
| 1 | 合规与私域双保险 | 客户/报价数据永不共享，公司没有"数据被平台拿走"的顾虑 |
| 2 | 共享的是"提炼物"不是"原始数据" | 匿名化+抽象化后共享，既成长又不泄露 |
| 3 | 沉淀中心质量可控 | 只收优质物、垃圾剔除——共享层质量有把关 |
| 4 | 语义与数据解耦 | 数据隔离不影响语义沉淀，平台照常从实践中学习 |
| 5 | 分型聚焦 | 2-3 类相似公司共用一套概念，避免"试图覆盖一切"的平庸 |
| 6 | 沉淀中心可独立演进 | 未来甚至可变成"行业基准/知识产品" |

### 7.4 劣势与风险

| # | 劣势/风险 | 说明 | 应对 |
| --- | --- | --- | --- |
| 1 | **提炼成本高（最大）** | 从原始数据到优质语义，需要持续的人工+AI 提炼、标注、评审 | 先建提炼模板与评审清单，沉淀质量优先级高于沉淀速度 |
| 2 | "垃圾"判定难 | 去噪去重需要标准和工具，误删好经验/留下坏经验都伤平台 | 定"沉淀准入标准"（有数据支撑/多公司验证/可复现） |
| 3 | 匿名化边界 | 抽象后的模式仍可能反推公司（如某公司特有工艺），需脱敏治理 | 提炼物只保留"模式"，不带公司标识与特征数值 |
| 4 | 贡献激励缺失 | 公司凭什么贡献经验？无激励则沉淀中心饿死 | 贡献可换"更好的推荐/更低服务费/行业榜单"，设计激励 |
| 5 | 分型切错 | "全包/半包/高端定制"若误当一类，流程差异互相拖累 | 分型以"流程差异度"为准，用真实公司验证边界 |
| 6 | 双体系工程复杂度 | 数据隔离 + 语义共享 = 两套存储与权限体系 | 现阶段只做"单公司 + 沉淀中心雏形"，多租户后置 |
| 7 | 早期样本不足 | 1-2 家公司时提炼物质量不可靠 | 前期靠行业资料补池，公司多了再启用分拣 |

### 7.5 结论
用户提出的"数据分离 + 语义分离分开"是正确的，且应成为平台的基本原则：**数据隔离管安全与私域，语义共享管平台成长**。落地时优先解决三件事：提炼质量、脱敏治理、贡献激励。
